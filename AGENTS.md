# AGENTS.md

Keep this file up to date.

Disposable-inbox email system for `*@wylynko.me`. **One Cloudflare Worker** serves
both the website and inbound mail — this repo is the merge of what used to be
three: `email-service` (Worker), `email-client` (Next.js on Vercel) and
`emails-cli` (Rust). Those still exist on GitHub, unarchived, as the pre-merge
history.

**The cutover happened on 2026-08-11**: `emails.wylynko.me` is a Custom Domain
on the `emails` Worker (the Vercel deployment is deleted), and both Email
Routing rules deliver to this Worker's `email()` handler. The old
`email-service` Worker still exists, unrouted, until it is decommissioned. See
"Migration status" at the bottom.

## Shape

```
worker.ts            entry: wraps .open-next/worker.js, adds the email() handler
src/                 Next.js App Router app (Clerk auth, Drizzle, R2, Workers AI)
src/middleware.ts    Clerk gate — NOT proxy.ts, see below
src/database/schema.ts   the single copy of the schema (was duplicated across two repos)
src/database/migrations/ drizzle-kit migrations; 0000 is an idempotent baseline
drizzle.config.ts    drizzle-kit config — migrations only, never read by the app
src/inbox/inboxQueries.ts    inbox reads/writes, shared by the website and /v1
src/email/emailQueries.ts    email/attachment reads, shared by the website and /v1
src/app/v1/              the CLI API (Bearer token, not Clerk)
cli/                 the Rust `emails` CLI (crate name `emails`, binary `emails`)
.env.schema          committed, value-free schema; varlock generates env.d.ts from it
worker-configuration.d.ts   generated by `pnpm generate-types` — do not hand-edit
worker-secret-vars.d.ts     hand-maintained: secret-store names merged into CloudflareEnv
```

## Deploying

**Deploys happen in CI only.** There is deliberately no `pnpm deploy` script —
deploying from a laptop is how a dev-built artifact ends up in production, and
the build must run under prod values because the Clerk publishable key is
inlined into client assets.

Cloudflare Workers Builds settings:

| field | value |
|-------|-------|
| Build command | `pnpm ci:build` |
| Deploy command | `npx wrangler deploy --env production` |

`--env production` is not optional. Without it CI publishes `emails-dev`, which
is bound to the clone, and the `emails` Worker never receives the build. The two
wrangler configs are named differently precisely so that mistake is visible
rather than silently pointing the live Worker at the clone.

`pnpm ci:build` authenticates a machine identity with `INFISICAL_CLIENT_ID` /
`INFISICAL_CLIENT_SECRET` (set as build secrets in the Cloudflare dashboard),
exports the resulting `INFISICAL_TOKEN`, and runs
`opennextjs-cloudflare build --env=production`. Pushing to `main` triggers a
Workers Builds build + deploy (verified live: a push lands as a new deployed
version within ~3 minutes).

The Infisical CLI is a devDependency, so `pnpm install` provides it — but it
ships its binary via a preinstall hook, so `@infisical/cli` must stay listed
under `onlyBuiltDependencies` in `pnpm-workspace.yaml`. Remove it there and pnpm
silently skips the hook, leaving no binary and a failing build.

### Build time and runtime need separate wiring

Infisical feeds two different places, and dropping either breaks something:

| | feeds | symptom if missing |
|---|---|---|
| `infisical run` around the build | varlock validation, and inlining public values into the artifact | build fails: "Value is required but is currently empty" (all 11 items) |
| Infisical → Cloudflare **secret sync** | the deployed Worker's runtime `env` | build and deploy succeed, then every request fails |

Nine values are read as `env.API_TOKEN`, `env.PUSHER_*` and so on — Cloudflare
binding lookups that only the Worker's secret store populates. `CLERK_SECRET_KEY`
is read by the Clerk SDK from `process.env`, which OpenNext fills from the same
store. **Build-time injection does not carry into the deployed Worker.**

The Infisical -> Cloudflare secret sync IS live (all 11 values from
`.env.schema` are in the Worker's secret store). Because the sync owns the
store, `wrangler secret put` must never be used — the next sync silently
overwrites it.

Deploying IS production now: the custom domain and Email Routing both point at
this Worker, so a bad deploy takes down the site, the CLI API and inbound mail
together. A failed `email()` handler is the quiet one of the three — senders
retry, rows duplicate, and nothing looks wrong from a browser. Tail the Worker
after deploying and watch a delivery land.

## Databases — read this before running anything

Two Neon databases, and they are **not** the same:

| | Endpoint | Hyperdrive config | Safe? |
|---|---|---|---|
| Production | `ep-purple-bread-a782nann` | `neon-email-database` `3c425a8db8…` | **NO — real mail** |
| Dev clone | `ep-twilight-sunset-a76wg4dm` | `neon-email-database-dev` `1b02e5c500…` | yes, develop here |

`wrangler.jsonc` has no top-level bindings: `env.development` (`emails-dev`
Worker, dev Hyperdrive) and `env.production` (`emails` Worker, prod Hyperdrive,
`emails.wylynko.me` custom domain) each carry their own. Verified safety
properties:

- **`wrangler dev` cannot reach production.** Miniflare refuses to use a remote
  Hyperdrive locally — it errors demanding
  `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE`. That variable
  lives in Infisical's dev environment and points at `ep-twilight-sunset`.

  The dev branch is disposable and has been recreated before (it was
  `ep-flat-king-a7yv3mu7` until 2026-08-11). Deleting it does not fail loudly:
  Neon's proxy cannot route to a dead endpoint, so every query comes back
  `28P01 password authentication failed` — which reads as a stale credential,
  not a missing database. Recreate either by branching from production or, since
  drizzle-kit landed, by pointing `MIGRATIONS_DATABASE_URL` at the blank database
  and running `pnpm db:migrate:dev` — migration `0000` builds the whole schema
  from scratch (verified against an empty database). After recreating, update BOTH
  `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE` in Infisical dev
  (local dev reads this) and the `neon-email-database-dev` Hyperdrive origin
  via `wrangler hyperdrive update` (the deployed `emails-dev` Worker reads
  that). Updating only the first leaves local dev working and the Worker broken.
- **`wrangler dev --remote` DOES use the deployed Hyperdrive config.** Never use
  that flag on this project.
- **Hyperdrive query caching must stay disabled** on the prod config
  (`caching: {disabled: true}`, set 2026-08-11). It once had `max_age: 3600`,
  which served the homepage's inbox-list aggregate from an hour-old snapshot
  while the per-inbox query (a different cache key) looked fresh — new mail
  notified instantly but never reordered the list. Looks exactly like a Next.js
  caching bug; it isn't. Caching is a dashboard/API setting on the Hyperdrive
  config, not in wrangler.jsonc. The dev config still has default caching
  (60s) — if dev reads ever look stale, that's why.

## Migrations

drizzle-kit owns schema changes. `src/database/schema.ts` is still the single
definition — migrations are generated *from* it, never hand-written to diverge
from it.

```bash
pnpm db:generate      # diff schema.ts against the last snapshot -> a new .sql
pnpm db:check         # verify the migration files and journal are consistent
pnpm db:migrate:dev   # apply to the dev clone
pnpm db:migrate:prod  # apply to production — real mail, see below
pnpm db:studio:dev    # drizzle studio against the dev clone
```

Both migrate scripts are wrapped in `infisical run`, so they read
`MIGRATIONS_DATABASE_URL` from the matching environment. **That variable is not
`DATABASE_URL` on purpose** — the old `DATABASE_URL` was deleted at the
Hyperdrive cutover, and reviving the name would imply the running app takes a
connection string again. It doesn't: the app only ever reaches Postgres through
the `HYPERDRIVE` binding. `MIGRATIONS_DATABASE_URL` is used by drizzle-kit and
the seeder, nothing else.

It must point at the **unpooled** Neon endpoint — the host *without* `-pooler`.
The pooled endpoint is pgbouncer in transaction mode; Hyperdrive talks to it for
ordinary queries, but it is the wrong target for DDL.

**Migration `0000` is an idempotent baseline.** It describes the schema as it
already existed when drizzle-kit was introduced, using `CREATE TABLE IF NOT
EXISTS` and an exception-guarded `ADD CONSTRAINT`. That is what let the two live
databases come under migration control without hand-inserting rows into
`drizzle.__drizzle_migrations`, and it is also why a blank database can now be
built from scratch. Verified both ways: applied cleanly to the existing dev
clone (the guards fire as `already exists, skipping` notices), and built a
complete schema in a freshly created empty database.

Hand-editing a generated `.sql` does **not** break future diffs — drizzle-kit
compares `meta/*_snapshot.json`, not the SQL text.

**Deploy order matters and there is no automation for it.** Migrations do not
run in CI; the Worker deploy does. So a change that adds a column has to be
migrated *before* the code that reads it is pushed, or the deployed Worker
queries a column that isn't there yet. Run `pnpm db:migrate:prod`, confirm it,
then push.

## Running it

```bash
pnpm dev              # next dev -H 0.0.0.0 on :3000 — hot reload, the daily driver
pnpm preview          # preview:build + opennextjs-cloudflare preview on :8787 — real workerd
pnpm preview:build    # BUILD_INFISICAL_ENV=dev opennextjs-cloudflare build --env=development
pnpm typecheck        # next typegen + pnpm generate-types + tsc --noEmit
pnpm generate-types   # wrangler types --env=development -> worker-configuration.d.ts
pnpm db:migrate:dev   # apply migrations to the dev clone (see "Migrations")
pnpm db:seed:dev      # fill the dev clone with fake mail (see "Seeding dev")
pnpm build            # next build; prod Infisical values unless BUILD_INFISICAL_ENV says otherwise
pnpm ci:build         # CI only: machine-identity login + opennextjs-cloudflare build
```

**Develop on `pnpm dev`.** It is `next dev`, so edits hot-reload and there is no
build step. `initOpenNextCloudflareForDev()` in `next.config.ts` gives it the
real bindings through miniflare, so `getCloudflareContext()` works.

That call **must** be passed `{ environment: "development" }`. `wrangler.jsonc`
has no top-level bindings, so the bare `initOpenNextCloudflareForDev()` loads an
empty binding set and the first Hyperdrive query dies with `Cannot read
properties of undefined (reading 'connectionString')`.

Reach for `pnpm preview` only to check something workerd-specific before
shipping. It serves the `.open-next/` artifact, so nothing you edit appears
until it rebuilds — and it binds :8787 while `pnpm dev` binds :3000, so both can
run at once.

Both bind `0.0.0.0`, not localhost, because this box is developed on remotely:
`dev.ip` in `wrangler.jsonc` for the wrangler side, `-H 0.0.0.0` for Next.
`allowedDevOrigins` in `next.config.ts` must also list the hostname you browse
from, or Next rejects the cross-origin dev request.

### The build environment decides which Clerk instance you get

`opennextjs-cloudflare build` does not call `next build` directly — it shells
out to the packager (`pnpm build`) via `buildNextjsApp` in
`@opennextjs/aws/dist/build/buildNextApp.js`. So the `build` script's own
`infisical run` wins over any wrapper around it: `infisical run --env=dev --
opennextjs-cloudflare build` still built under **prod** values, because the
inner call said `--env=prod`.

That matters because the Clerk publishable key is inlined into the client chunks
at build time (see `.env.schema`). A prod-built artifact served by `wrangler dev`
loads production Clerk, which rejects `localhost` and every other non-production
origin with a 400 `origin_invalid` — an error that looks like a CORS or hostname
problem and is neither.

Hence `BUILD_INFISICAL_ENV`: `build` reads `--env=${BUILD_INFISICAL_ENV:-prod}`,
so CI and `pnpm build` keep their prod default and only `preview:build` overrides it.
Check which instance an artifact carries with:

```bash
grep -rhoE 'pk_(live|test)_[A-Za-z0-9=]+' .open-next/assets/ | sort -u
```

The old `preview` / `deploy` / `deploy:dev` / `dev:worker` / `cf:build` /
`cf-typegen` scripts and the `scripts/` directory were deleted in the manual
rework of 2026-08-10 — CI is the only build-and-deploy path now.

**There are no `.env` files with values, and there is no `.dev.vars`.** Secrets
live in Infisical (project "emails", environments `dev` and `prod`) and are
injected by the Infisical CLI; `.env.schema` is the committed, value-free schema
that varlock validates against. See `~/SECRETS.md` for the model.

Every script is already wrapped in `infisical run`, so there is nothing to
remember — but if you invoke a build or the Worker directly, wrap it yourself or
it will fail on missing values.

Two things that are NOT in Infisical, on purpose:

- `NEXT_PUBLIC_CLERK_SIGN_IN_URL` — a non-secret whose value is declared in
  `.env.schema`. Being public it is inlined at build time, so the Worker never
  needs it at runtime.
- The Cloudflare bindings (`HYPERDRIVE`, `ATTACHMENTS`, `AI`, `ASSETS`), which
  come from `wrangler.jsonc`.

`wrangler dev` does not forward its own process environment into the Worker's
`env` — that is what `.dev.vars` normally exists for, and there isn't one. The
fetch path doesn't care (varlock's ENV is initialized from the build), but the
`email()` path reads secrets from `env` (see "The mail handler"), so local
synthetic-mail runs will find `env.PUSHER_*` etc. undefined. Test the mail
pipeline against the deployed Worker with a muted inbox instead.

**Browse `wrangler dev` on `http://localhost:8787`, not `127.0.0.1`.** Wrangler
forwards `x-forwarded-host: localhost`, and Next rejects Server Actions whose
`Origin` doesn't match — you get a 500 on any action, including the Clerk
`/authenticate` ticket flow.

## Next 16 on Cloudflare — the constraints

- **The Clerk gate must live in `src/middleware.ts`, not `proxy.ts`.** Next 16
  renamed the convention and moved `proxy` to the Node.js runtime, where the
  `runtime` option is not configurable and setting it throws. OpenNext cannot run
  Node middleware, so `proxy.ts` fails the build outright. The Next 16 upgrade
  guide's own words: "If you want to continue using the `edge` runtime, keep
  using `middleware`." Revisit when OpenNext supports Node middleware
  (cloudflare/workers-sdk#13755).
- **`pg` cannot be bundled.** It requires the optional `pg-cloudflare` native
  companion, which esbuild can't resolve through pnpm's layout even when it is
  installed. Use **postgres.js** (`drizzle-orm/postgres-js`) with
  `{ prepare: false }` — Hyperdrive pools connections, so named prepared
  statements are not safe.
- **`assets` must be bound in `wrangler.jsonc`** (`.open-next/assets`). Without
  it the app serves HTML fine and every chunk, stylesheet and image 404s — which
  looks like a working app to a curl check.
- **Two compatibility flags are required**, not one: `nodejs_compat` *and*
  `global_fetch_strictly_public`. Missing the second means a server-side
  `fetch()` to a URL matching this Worker's own routes loops back internally
  instead of going out to the public internet.
- Keep `compatibility_date` roughly current with the installed workerd, or every
  build prints a staleness warning.
- **`initOpenNextCloudflareForDev()` must be guarded** to `NODE_ENV ===
  "development"`. `next.config.ts` is evaluated during `next build` too, and that
  call starts miniflare, which refuses to emulate Hyperdrive without
  `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_HYPERDRIVE`. That variable
  exists only in the dev environment, so an unguarded call fails every CI build
  with "you should use a local Postgres connection string" — a message that
  sounds like a local-setup problem while actually breaking production builds.
- `main` is `worker.ts`, not the adapter's default `.open-next/worker.js` — that
  is the documented custom-worker override, and it is what allows `email()` to
  live alongside `fetch`.
- **Never build the database client at module scope.** Module scope outlives a
  request inside a Worker isolate, so request 2 touches promises created in
  request 1's context and workerd cancels it with "your Worker's code had hung
  and would never generate a response" — instantly, in ~10ms, despite the
  wording. It failed on exactly every other request:

  | driver | six consecutive requests |
  |--------|--------------------------|
  | module-scope `@neondatabase/serverless` | 200, 500, 200, 500, 200, 500 |
  | per-request Hyperdrive + postgres.js | 200 × 6 |

  Fixed: `getEmailsDb()` in `src/database/index.ts` is wrapped in React
  `cache()`, so one client is shared within a request and never across requests.
  Easy to misdiagnose — alternating failures over a list of different inputs read
  exactly like "these particular records are broken". They are not.

- **The R2 bucket in `wrangler dev` is local and empty**, so attachment
  downloads 404 against a fresh checkout even though the database row exists.
  Seed one to exercise the path:
  `npx wrangler r2 object put email-attachments/<r2Key> --file=x --local`

## Secrets and types are linked

`wrangler types` learns var names from `.dev.vars`, and there isn't one — so the
generated `CloudflareEnv` only knows the bindings. The secret-store names are
declaration-merged in by the hand-maintained `worker-secret-vars.d.ts`. Adding a
variable therefore means: add it in Infisical (both environments), add it to
`.env.schema` (env.d.ts regenerates from it), and add it to
`worker-secret-vars.d.ts` if the `email()` path reads it.

**The built artifact is environment-specific.** Public values are inlined into
client assets at build time, so a dev build carries dev values — which is why
the only deploy path is CI building under prod Infisical values.

varlock scans build output for leaked secret values and fails the build if it
finds one. Two values legitimately reach the browser and are marked `@public` for
that reason: `PUSHER_KEY` / `PUSHER_CLUSTER` (the browser subscribes with them)
and `BEAMS_INSTANCE_ID` (the Beams SDK registers a device with it). All three are
passed from server components as props rather than via `NEXT_PUBLIC_` prefixes,
so they resolve at runtime. `PUSHER_SECRET` and `BEAMS_SECRET` are the actual
secrets and never leave the Worker.

## Types

`pnpm generate-types` runs `wrangler types --env=development` into
`worker-configuration.d.ts` (runtime globals + the binding half of
`CloudflareEnv`, one file — the old two-file split-and-strip generator is
gone). It declares `mainModule: typeof import("./worker")`, which drags
`worker.ts` into the TS program; the `@ts-ignore` on worker.ts's
`.open-next/worker.js` import is what lets a clean checkout typecheck anyway.

Note the runtime globals override the DOM lib, so `Response.json()` returns
`unknown` rather than `any` in client components. Type the result.

## The mail handler

**Secrets in the email vertical come from the `env` parameter, never
`varlock/env`'s `ENV`.** varlock is initialized (and `process.env` populated
from the secret store) by OpenNext's fetch path only. On a cold isolate,
`ENV.X` inside `email()` throws "varlock ENV not initialized" — *after* the
INSERT, so Email Routing retries and duplicates the row. On a warm isolate a
prior fetch has initialized it and the same code works, which makes the bug
look intermittent. This took down mail for ~15 minutes during the 2026-08-11
cutover; `worker-secret-vars.d.ts` documents the rule.

The cheapest live end-to-end test: mute an inbox
(`PUT /v1/inboxes/<to> {"silent": true}` — it upserts), send real mail to it
via the Resend API, and `wrangler tail emails` to watch `receiveEmail` log and
the event report `Ok`.

`receiveEmail()` can also be exercised synthetically — construct a
`ForwardableEmailMessage` yourself (`from`, `to`, `headers` and a `raw`
ReadableStream over a MIME string) and call it with `env` — but note local
`wrangler dev` has no secret store, so the notification steps only work
deployed.

Two things to get right when testing:

- **Force the target inbox `silent: true` first**, or the run pages a real phone
  through Pusher Beams and Techulus.
- Resend is constructed lazily, inside the forward-on branch only. Its
  constructor throws on a missing key, so building it eagerly makes every
  ordinary delivery depend on a credential it never uses — and since Email
  Routing retries a failed delivery, that would duplicate rows for all inbound
  mail. Keep it where it is.

## The /v1 CLI API

Route handlers under `src/app/v1/`, authorised by `src/api/authorizeApiToken.ts`
(Bearer, timing-safe). Two halves of one decision, and breaking either is silent:
`middleware.ts` lists `/v1` as public so Clerk does not redirect token requests,
and `withApiToken` is what actually guards them.

`PUT /v1/inboxes/:to` still accepts `silent` only. `receiver` remains
website-only on purpose — that dropdown restricts it to addresses that have
already mailed the inbox.

Test it with the real CLI rather than curl:

```bash
EMAILS_API_URL=http://localhost:8787 EMAILS_API_TOKEN=<token> emails inboxes
```
